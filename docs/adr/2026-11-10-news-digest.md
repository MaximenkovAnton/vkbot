# 2026-11-10: «Что нового» — консюмер `NEWS_DIGEST_REQUESTED`, период из текста и LLM-сводка

- **Статус:** accepted
- **Дата:** 2026-11-10
- **Supersedes:** —

## Контекст

Маршрутизация интентов (ADR 2026-11-09-decision-runtime-spam-policy, доставлена board-task `intent-routing-help-v2`) публикует после
`requiredAnswer=true` ровно одно событие по интенту: `help` → `ANSWER_MESSAGE` со справкой,
`news` → `NEWS_DIGEST_REQUESTED` с доменным `Message`, `general` → `MESSAGE_REQUIRE_ANSWER`.
`NEWS_DIGEST_REQUESTED` — седьмое значение закрытого `enum class Event` — потребителя не имеет: диспетчер
не находит `EventProcessor` по routing key, пишет ERROR с целым payload (текст сообщения, PII) и
подтверждает событие. Пользователь, спросивший «что нового за вчера», ответа не получает, а
промежуточное состояние «событие без консюмера» не деплоится.

Решение человека (R5/R6): «что нового» отвечает LLM-сводкой в `:src:ai`; период берётся из текста
запроса (относительные и абсолютные даты), явный срок длиннее 7 суток отклоняется, без указания срока
период начинается от последнего сообщения этого автора в чате (не более 7 суток); свежие сообщения —
не больше `summary.batch-size`; в `summaries` ничего не пишется.

## Решение

- **Форма сценария.** Отдельная вертикаль «что нового» внутри существующего `:src:ai`, поток
  `adapter input → port input → usecase → command → port output → adapter output`: консюмер
  `NewsDigestRequestedEventProcessor` (`@All processors` собирает его автоматически) → входной порт
  `ProcessNewsDigestInputPort` → тонкий `ProcessNewsDigestUsecase` → `ProcessNewsDigestCommandImpl` →
  `NewsDigestGenerationPort` / `PublishEventCommand`. Новых модулей, событий, payload-классов, очередей,
  REST-эндпоинтов и второго деплоя нет.
- **Три read-only `share`-порта** (`share/port/output/persistence/`), реализованные `:src:persistence`
  in-process на существующих таблицах `messages`/`summaries`:

  | Порт | Запрос | Ответ |
  |---|---|---|
  | `FindLastStoredMessageByAuthorPort` | `peerId`, `fromId`, `beforeConversationMessageId` | последнее сообщение автора до указанного id или `null` |
  | `FindStoredMessagesBetweenDatesPort` | `peerId`, `from`, `to`, `limit` | ≤ `limit` последних по `conversationMessageId` сообщений с `date ∈ [from, to]`, по возрастанию id |
  | `FindStoredSummariesInPeriodPort` | `peerId`, `from`, `to` | только `COMPLETED`-саммари, чей id-диапазон пересекает период, по `createdAt` ASC |

  `PersistenceDataInputPort`/`PersistenceDataRequest`/`PersistenceDataResponse` расширены аддитивно,
  in-process адаптеры делегируют в них, как существующие; публичный REST `/persistence/*` не меняется.
  Схема БД и Liquibase не меняются.
- **Правила периода** — чистый домен `NewsPeriodParser.parse(text, reference)`, где `reference` — дата
  сообщения-запроса. Календарный день считается в offset-е `reference`, границы дня — `00:00:00.000000000`
  и `23:59:59.999999999`. Авторитетная таблица форм:

  | Форма (регистр не важен) | Период `[from, to]` |
  |---|---|
  | «сегодня», «вчера», «позавчера» | границы календарного дня `reference`, предыдущего, позапрошлого |
  | «за N дней», «за последние N дней» (N = 1..999) | `[reference.minusDays(N), reference]`; N = 0 или числа нет → срок не найден |
  | «за неделю», «за последнюю неделю», «эта неделя», «последняя неделя», «на этой неделе» | `[reference.minusDays(7), reference]` |
  | `DD.MM`, `D <месяц>` | границы одного дня, год выводится |
  | `DD.MM.YYYY`, `D <месяц> YYYY` (+ «года»/«г.») | границы указанного дня; явный год используется как указан |
  | «с 1 по 3 ноября», «с 1 ноября по 3 ноября 2026» | включительные границы; год конца выводится ≤ `reference` по календарной дате, год начала — не позже конца (переход года допустим) |
  | срок не найден, невалидная дата, `from > to` | `null` |

  Приоритет форм: диапазон «с … по …» → одиночная абсолютная дата → «сегодня/вчера/позавчера» → неделя →
  «за N дней»; совпавшая, но невалидная абсолютная форма даёт `null`, к следующей форме не переходим.
  Год одиночной даты: текущий год `reference`, если дата в нём валидна и не позже даты запроса, иначе
  предыдущий. Явно указанный будущий год допустим — период уходит в пустоту и даёт «Нет сообщений».
  Явный срок длиннее 7 суток (`Duration.between(from, to) > Duration.ofDays(7)`) отклоняется фиксированным
  ответом. Срок не найден → команда строит период сама: `to` — дата запроса, `from` — дата последнего
  сообщения автора, если оно есть, не позже `to` и не старше 7 суток, иначе `to.minusDays(7)`.
- **Сборка данных для LLM.** `FindStoredSummariesInPeriodPort` даёт `shortSummary` завершённых саммари
  (пустые и пробельные пропускаются); `FindStoredMessagesBetweenDatesPort` — свежие сообщения с
  `limit = summary.batch-size`, из которых исключено само сообщение-запрос (вопрос, а не контент) и всё,
  что уже вошло в саммари периода (`conversationMessageId <= max(lastMessageId)`). Авторы форматируются
  общим компонентом `MessageAuthorFormatter` (извлечён из `GenerateSummaryCommandImpl`, формат не
  изменился): `[Имя Фамилия]`, имя группы по `-fromId`, fallback `Пользователь N`/`Группа N`, профили
  людей и групп запрашиваются раздельно. Данные — две секции с заголовками «Сводки обсуждений за
  период:» и «Сообщения за период:»; заголовок попадает в данные, только если секция непустая; между
  секциями ровно одна пустая строка. Период в данные не добавляется: он уже отражён составом.
- **LLM с повторами и фолбэком.** `NewsDigestGenerator` — `@RegisterAiService` без инструментов и без
  памяти чата, system-промпт из `{config:aiNewsDigestSystemprompt}`; `NewsDigestAiAdapter` делает ровно
  три попытки, пустой или пробельный ответ модели — неудачная попытка, после третьей — новый
  `NewsDigestGenerationException` (`VkBotAppException`, `EXTERNAL_FAILURE`) с последним `cause`. Финальный
  отказ не уходит в брокер: команда публикует фиксированный текст «Не удалось собрать сводку. Попробуйте
  позже.» и пишет ERROR только с `peerId` и простым именем класса исключения. Ошибки чтения БД и
  публикации не перехватываются — уходят в retry-лестницу брокера.
- **Публикация — из команды (A1).** `ProcessNewsDigestCommandImpl` инжектит `PublishEventCommand` и
  публикует ровно один `ANSWER_MESSAGE` с `ResponseMessage(messageText, responseTo = исходное Message)`;
  `SUMMARY_REQUESTED`/`SUMMARY_READY` не публикуются, в `summaries` ничего не пишется (write-портов
  саммари в команде нет — структурное доказательство). Это отклонение от обычая «публикует use case»
  (`GenerateAnswerUsecase`): у команды один вызывающий и один повод к изменению, а приёмочные критерии
  называют тестом именно команду. Условие апгрейда: появится второй потребитель текста digest —
  публикация переезжает в use case.
- **PII.** Текст чата уходит в LLM-промпт; глобальные `quarkus.langchain4j.log-requests/log-responses:
  true` логируют его на INFO и экспортируют по OTLP — тот же принятый риск, что ответы и саммаризация
  (ADR 2026-11-05-llm-provider-vllm-openai, ADR 2026-11-08-decision-model-langchain4j). Инструментов у AI-сервиса нет, поэтому prompt injection не даёт действий; новый код
  текст не логирует.
- **Конфигурация** (единственный конфиг `:src:app`, ADR 2026-10-28-configuration-and-secrets):

  ```yaml
  aiNewsDigestSystemprompt: ${NEWS_DIGEST_SYSTEM_PROMPT:Ты — помощник, который кратко пересказывает, что происходило в чате. Пиши по-русски, структурировано, без выдумок.}
  ```

  Ключ читает `NewsDigestGenerator`; `summary.batch-size` переиспользуется как лимит свежих сообщений.
  Новых обязательных env нет: `NEWS_DIGEST_SYSTEM_PROMPT` опционален, дефолт в [`application.yml`](../../src/app/src/main/resources/application.yml).
- **Совместимость и раскатка.** Части 2 и 3 выкатываются вместе: промежуточное состояние «событие без
  консюмера» не деплоится. Порядок «env → образ» не требуется; топология RabbitMQ не меняется.
- **Откат.** Предыдущий образ; данные и схема не меняются, флагов нет. Откат возвращает потерю запросов
  «что нового» (unknown routing key → ERROR с payload) — известно и приемлемо.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Создать саммари и опубликовать `SUMMARY_READY` | Запрещено решением человека (R6): digest ничего не пишет и не переиспользует конвейер саммаризации; иначе понадобились бы write-порты и новая запись в `summaries` |
| Собирать digest только из сообщений, без саммари | Теряется уже свёрнутый контекст старых обсуждений периода; `shortSummary` завершённых саммари — готовый источник |
| Отдельный сервис/событие на каждый источник данных | Нет требования: оба чтения — in-process порты одного деплоя, событие уже опубликовано |
| Собственный outbox/дедупликация | Нет требования; дубли at-least-once — известный размен, как у ответов и справки; VK дедуплицирует по детерминированному `random_id` |
| Per-chat timezone | Вне allowlist: календарный день считается в offset-е сообщения (в дереве — UTC); бизнес-зона — отдельное решение с ключом и ADR |
| Переносить публикацию в use case | У команды один вызывающий; перенос 5 строк — условие апгрейда при появлении второго потребителя текста digest |

## Известные пробелы (named gaps)

- Нет rate limit/анти-флуда на «что нового»: LLM-вызов на каждый запрос (до трёх попыток порта); при
  at-least-once повторная доставка события даёт повторный LLM-вызов и повторный ответ, собственного дедупа
  и outbox нет.
- Календарный день — в offset-е сообщения; Long Poll отдаёт UTC, поэтому «сегодня/вчера» — UTC-дни (для
  UTC+3 граница смещена); бизнес-зона чата — отдельное решение.
- Саммари периода не клипуются по датам: берётся `shortSummary` саммари, чей id-диапазон пересекает период,
  поэтому на границе периода в сводке возможно лишнее.
- `max-tokens` не задан, усечения промпта нет: отказ провайдера по длине контекста даёт фолбэк.
- Тексты ответов («Слишком длинный срок: сводка возможна максимум за неделю.», «Нет сообщений за этот
  период.», «Не удалось собрать сводку. Попробуйте позже.») — литералы кода.
- Нет метрик и спанов digest, отдельного INFO-лога успеха: наблюдаемость — брокерская, OTLP-логи и ERROR
  при отказе LLM.
- Индексов под новые чтения нет: `findLastByAuthor` сортирует по `conversation_message_id`, а `findByPeriod`
  ограничивает `EXISTS` окном `conversation_message_id` периода и всё ещё сканирует саммари peer'а.
  Апгрейд — changeset `007` с `messages(peer_id, conversation_message_id)` (и, при росте числа саммари,
  `summaries(peer_id, first_message_id)`), а не `(peer_id, date)`: составной индекс по дате этот план не
  ускоряет. Условие — медленный p95 digest (вне allowlist).

## Последствия

- Появился третий producer `ANSWER_MESSAGE` (после `ai-answer` и веток `answer-decision`); контракт
  события и `ResponseMessage` не менялся.
- Седьмое событие получило консюмера; промежуточное состояние «событие без потребителя» больше не
  существует. Публичный REST и схема БД не менялись.
- Текст чата уходит в LLM-промпт и в INFO/OTLP-логи провайдера — новый принятый PII-поток (ADR 2026-11-05-llm-provider-vllm-openai, ADR 2026-11-08-decision-model-langchain4j).
- Стоимость: LLM-вызов (до трёх попыток порта) на каждый запрос «что нового»; лимитов нет (named gap).
