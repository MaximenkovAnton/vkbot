# ADR 0008: Приём событий VK через Bots Long Poll вместо Callback API

- **Статус:** accepted
- **Дата:** 2026-11-05
- **Supersedes:** —

## Контекст

Входящие события сообщества VK приходили на `POST /vk/callback` в `receiver`. Из этого следовало три
ограничения. Первое: деплой обязан быть доступен из интернета и держать публичный HTTP-вход. Второе:
`receiver` проверял секрет `vk.secret` и отвечал на `confirmation` кодом `vk.confirmation-code` — два
обязательных ключа конфигурации только ради транспорта (ADR 0006). Третье: пока приложение остановлено,
VK ретраит доставку и после серии попыток отбрасывает событие, поэтому сообщения за время простоя и
деплоя терялись без следа.

Bots Long Poll API решает все три: приложение само опрашивает VK по исходящему HTTP и позицию опроса
можно хранить, чтобы продолжить чтение после рестарта.

## Решение

- `receiver` опрашивает Bots Long Poll API. Сессия — `groups.getLongPollServer` через существующий
  REST-клиент `configKey: "vk"` (`quarkus.rest-client.vk.url` = `https://api.vk.ru/method`), затем
  `a_check` по адресу `server` из ответа: `{server}?act=a_check&key=…&ts=…&wait=25`. `server` и `key`
  сессии не хранятся — на старте сессия запрашивается заново; `ts` хранится только как позиция опроса.
  Read-timeout клиента — 60 с, иначе 25-секундное ожидание VK рвёт соединение на холостом ответе.
- Драйвер опроса — `com.simarel.vkbot.receiver.adapter.input.vk.LongPollRunner`: виртуальный поток,
  старт по `StartupEvent`, остановка по `ShutdownEvent`, включение ключом `vk.longpoll.enabled`
  (`VK_LONGPOLL_ENABLED`, по умолчанию `true`). Паузы: 5 с при сбое публикации, нарастающая до 60 с при
  сетевых ошибках и 5xx (сброс после успеха). Коды `failed` обрабатываются по матрице: `1` — продолжить
  с новым `ts` из ответа (часть истории VK потерял, WARN), `2` — новая сессия с тем же `ts`, `3` — новая
  сессия и `ts` из `groups.getLongPollServer`.
- Позиция опроса `ts` — данные, а не конфигурация: она лежит в PostgreSQL в таблице `long_poll_position`
  (changeset `005-create-long-poll-position-table`, Liquibase) и доступна через share-порты
  `FindLongPollTsPort` / `SaveLongPollTsPort`, реализованные `PersistenceDataInProcessAdapter` в
  `persistence`. Позицию сохраняет драйвер, а не use case: `ts` — состояние транспорта.
- `ts` сохраняется только после успешной публикации `MESSAGE_NEW` в RabbitMQ. Падение между публикацией
  и сохранением даёт повторную доставку того же обновления (дубликат), сохранение до публикации дало бы
  потерю.
- Callback удалён целиком: нет `POST /vk/callback` ни для одного профиля (ответ — 404), нет
  `vk.secret`/`vk.confirmation-code` и env `VK_SECRET`/`VK_CONFIRMATION_CODE`, нет декоратора проверки
  секрета, `ConfirmationCode` и `ExceptionHandler`; `VkCallbackEvent` переименован в `VkUpdateType`
  (`MESSAGE_NEW`, `MESSAGE_REPLY`, `UNKNOWN`), вход use case — `ReceiveMessageInputPort` с запросом
  `VkUpdateInputPortRequest(type, message)`. `MessageMapper` не менялся: у обновления Long Poll те же
  `object`/`group_id`.
- HTTP-клиент Long Poll живёт в `receiver`: входящий транспорт принадлежит ему, а `vk-facade` остаётся
  владельцем исходящих вызовов VK API.
- Новый обязательный ключ — `vk.group.id` (`VK_GROUP_ID`), положительный id сообщества для
  `groups.getLongPollServer`. `vk.bot.id` не переиспользуется: у него не гарантирован знак (он сравнивается
  с `from_id`), а методу нужен именно положительный id сообщества.
- Деплой остаётся один (`:src:app`, ADR 0002): `quarkus-scheduler` не добавлялся, второго деплоя и нового
  Gradle-модуля нет.

## Последствия

- Публичный HTTP-вход продукту больше не нужен: приложение работает за NAT и не требует проброса порта,
  обратного прокси и TLS-терминации для VK.
- Поддерживается ровно один экземпляр приложения: два экземпляра с одним токеном и одной сохранённой
  позицией делят `ts` и мешают друг другу, поэтому горизонтальное масштабирование приёма не поддерживается.
- Гарантия при сбое публикации — «дубликат вместо потери»: повторная публикация того же обновления
  допустима, идемпотентности записи в `messages` по-прежнему нет.
- `failed: 1` означает, что VK уже отбросил часть истории; опрос продолжается с нового `ts`, а потеря
  фиксируется WARN-логом.
- Битое или неизвестное обновление пропускается с ERROR, `ts` сохраняется: теряется одно обновление, цикл
  не останавливается.
- Новый обязательный env `VK_GROUP_ID` и удалённые `VK_SECRET`/`VK_CONFIRMATION_CODE` меняют контракт
  деплоя: старый образ с прежними переменными и новый образ одновременно не запускаются одним набором env.
- Появилась таблица `long_poll_position`; её читает и пишет только `persistence`, схема остаётся его
  владением.
- Переключение сообщества делает человек в настройках VK: сначала включить Bots Long Poll с событием
  `message_new`, затем отключить Callback API, затем выкатить образ без `VK_SECRET`/`VK_CONFIRMATION_CODE`
  и с `VK_GROUP_ID` (порядок — `docs/development/deployment.md`).

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Оставить Callback API | Публичный HTTP-вход, обязательный секрет и потеря событий за время простоя — те же три ограничения; Long Poll снимает их без второго деплоя |
| `ts` в памяти процесса | Рестарт начинает с `ts` сессии и теряет всё, что пришло за время простоя, — ровно та проблема, ради которой затевался переход |
| `ts` в файле или env | В контейнере файловая система эфемерна, env меняется только редеплоем; позиция — изменяемые данные, её место в PostgreSQL рядом с остальным состоянием |
| `quarkus-scheduler` и фоновые задачи | Цикл опроса — один виртуальный поток на старте приложения; планировщик добавил бы расширение и второй способ запуска без требования |
| Второй деплой или Gradle-модуль под Long Poll | Приём — часть `receiver`; отдельный процесс потребовал бы второго раннера (запрещено ADR 0002) и общей позиции `ts` |
| Оставить `/vk/callback` «на один релиз» | Два транспорта с разными контрактами и ключами; ветвление по флагу усложнило бы код без требования |
