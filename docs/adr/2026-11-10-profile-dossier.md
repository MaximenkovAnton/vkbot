# 2026-11-10: «Профиль» — детерминированный резолв адресата, досье из сохранённых данных и LLM-ответ

- **Статус:** accepted
- **Дата:** 2026-11-10
- **Supersedes:** —
- **Amended by:** ADR 2026-11-11-profile-knowledge-overlay — секция `Из общения:` из знаний чата и
  fail-open опционального чтения знаний (единственное исключение из правила «ошибки чтения и публикации
  не перехватываются» ниже).

## Контекст

Маршрутизация интентов после `requiredAnswer=true` публикует по интенту ровно одно событие:
`help` → `ANSWER_MESSAGE` со справкой, `news` → `NEWS_DIGEST_REQUESTED`, `general` →
`MESSAGE_REQUIRE_ANSWER` (ADR 2026-11-09-decision-runtime-spam-policy). Board-таска
`profile-data-and-intent` добавила четвёртый интент `profile` и `PROFILE_REQUESTED` с доменным
`Message` — восьмое значение закрытого `enum class Event`; консюмера у события не было, поэтому
пользователь, спросивший «что ты знаешь о Паше Селезневе» или «обо мне», ответа не получал, а
промежуточное состояние «событие без консюмера» не деплоится.

Данные для ответа уже лежат в PostgreSQL: человеческий профиль VK с историей изменений
(ADR 2026-11-10-vk-profile-human-details) и материализованная статистика автора
(ADR 2026-11-10-user-statistics-materialization). Решения человека (ledger задачи `126f16cc`):
источники досье — профиль VK (typed + человеческие `details`), статистика и история; точка входа —
только интент decision-модели, отдельной `/профиль` нет; неоднозначность — одно сообщение со списком
кандидатов без состояния; по голому имени ищем только авторов этого `peer_id`; статистика в досье
включает разбивку по чужим чатам (осознанный PII-риск); ветка always-on, откат — предыдущий образ.

## Решение

- **Своя вертикаль внутри `:src:ai`.** Поток
  `adapter input → port input → usecase → command → port output → adapter output`: консюмер
  `ProfileRequestedEventProcessor` (`@All processors` собирает его автоматически) → входной порт
  `ProcessProfileInputPort` → тонкий `ProcessProfileUsecase` → `ProcessProfileCommandImpl` →
  `ProfileAnswerGenerationPort` / `PublishEventCommand` и `share`-порты чтения. 15 main-файлов в
  allowlist board-таски; **новых модулей, production-зависимостей, событий, payload-классов, очередей,
  таблиц, REST-эндпоинтов и второго деплоя нет** (ADR 2026-10-28-module-boundaries-and-layer-rules,
  ADR 2026-10-28-single-deployable-app-module). Форма повторяет `chat-news-digest`
  (ADR 2026-11-10-news-digest).
- **Резолв адресата — детерминированный домен, не модель.** Приоритет строгий: (1) mention-структуры
  `[idN|label]`, `[clubN|label]`, `[publicN|label]` и отдельные токены `idN`/`clubN`/`publicN`, причём
  упоминание самого бота (его id, id сообщества или `vk.bot.mention`) отбрасывается, а несколько id дают
  уточнение; (2) последнее пересланное сообщение с `fromId ≠ vk.bot.id`; (3) «обо мне»/«про меня» —
  автор сообщения; (4) фраза имени среди сохранённых профилей авторов этого `peer_id`. Один кандидат —
  цель, несколько — уточнение, ноль — «не нашёл». Каждый шаг — чистая функция с табличными тестами:
  `ProfileTargetResolver`, `ProfileNameNormalizer`, `ProfileNameMatcher` в `ai/domain/profile`.
  LLM получает уже определённого адресата и **пишет только текст** ответа.
- **Неоднозначность — одно сообщение, без состояния.** Уточнение перечисляет не больше 10 кандидатов в
  формате `N) Имя Фамилия (@screen_name, id<fromId>)` и не вызывает LLM; попытки «запомнить» ожидание
  ответа, `pending clarifications`, kill-switch и диалога уточнений нет — следующий запрос резолвится
  заново.
- **Досье — только сохранённые данные.** Профиль VK (typed + человеческие `details` по allowlist),
  материализованная статистика (глобальные агрегаты и разбивка по чатам, включая чужие), последние 20
  записей истории изменений, число сообщений цели в этом чате. Группа получает профиль группы и счётчик в
  этом чате — статистики и истории у групп нет. Текст собирает `ProfileDossierFormatter` — чистый домен,
  секции `Профиль:`, `Статистика:`, `История изменений:`, `В этом чате:`, пустые секции не пишутся;
  телефоны, контакты, `counters`, `connections`, неизвестные ключи и VK-id не рендерятся (allowlist
  выведен из `VkUserProfileMapper`, ADR 2026-11-10-vk-profile-human-details). Если сохранённого профиля
  нет, он запрашивается live через `GetUserProfilesBatchPort`/`GetGroupProfilesBatchPort` и **не
  сохраняется**; если VK не отдал профиль и там — «Профиль недоступен.» без LLM.
- **Один новый output-порт.** `ProfileAnswerGenerationPort` (`OutputPort<Request(question, data),
  Response(text)>`) + `ProfileAnswerGenerator` — `@RegisterAiService` без инструментов и без памяти чата,
  `@SystemMessage("{config:aiProfileSystemprompt}")` — + `ProfileAiAdapter`: ровно три попытки, пустой
  или пробельный ответ считается неудачной, после третьей — `ProfileGenerationException` со статусом
  `EXTERNAL_FAILURE` в единой иерархии `VkBotAppException` (ADR 2026-11-09-exception-hierarchy).
  Переиспользовать `GenerateAnswerOutputPort`/`UserAnswerGenerator` отклонено: у того сервиса память чата
  и Vane-инструменты, другой system-промпт, риск выдумок и расширение PII-egress, а свой ретрай поверх
  чужого адаптера — скрытая связность.
- **Ровно одна публикация `ANSWER_MESSAGE` из команды.** `ProcessProfileCommandImpl` инжектит
  `PublishEventCommand` и публикует `ResponseMessage(messageText, responseTo = исходное Message)`;
  при `ProfileGenerationException` — фиксированный текст «Не удалось собрать профиль. Попробуйте позже.»
  и ERROR только с `peerId` и простым именем класса исключения, без текста и PII; исключение в брокер не
  уходит. Ошибки чтения и публикации не перехватываются — уходят в retry-лестницу брокера. В БД ничего
  не пишется: write-портов у команды нет (структурное доказательство), `SUMMARY_*` не публикуются.
- **PII-egress — осознанно принятый риск.** В LLM-промпт уходят исходный вопрос, профиль и его
  человеческие `details`, история изменений профиля и статистика активности, включая активность в чужих
  чатах; глобальные `quarkus.langchain4j.log-requests/log-responses: true` логируют промпт и ответ на INFO
  и экспортируют по OTLP (ADR 2026-11-05-llm-provider-vllm-openai). Инструментов у AI-сервиса нет,
  поэтому prompt injection не даёт действий; новый код значения не логирует.
- **Конфигурация.** Единственный новый ключ — в `:src:app` (ADR 2026-10-28-configuration-and-secrets):

  ```yaml
  aiProfileSystemprompt: ${AI_PROFILE_SYSTEM_PROMPT:Ты — помощник, который собирает короткое человекочитаемое досье об участнике чата по данным ниже. Пиши по-русски, только по переданным данным, не выдумывай и не раскрывай служебные id, телефоны и контакты.}
  ```

  `AI_PROFILE_SYSTEM_PROMPT` опционален, дефолт в `application.yml`, новых обязательных env нет;
  `vk.bot.id`, `vk.bot.mention`, `vk.group.id` и `statistics.timezone` только читаются.
- **Always-on без kill-switch.** Как у `chat-news-digest`: отдельного ключа гашения ветки нет, откат —
  предыдущий образ; данные и схема при откате не меняются. Кэша ответов и rate limit нет: LLM-вызов (до
  трёх попыток порта) на каждый запрос; условие апгрейда — `decision.profile-reply.enabled` при требовании
  гасить ветку без отката и cooldown на `(peerId, userId)` при измеренном абьюзе.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Отдельный `/профиль` и состояние «жду уточнение» | Решение человека: точка входа — только интент decision-модели, без состояния и памяти; естественные фразы ловит модель |
| Переиспользовать `GenerateAnswerOutputPort`/`UserAnswerGenerator` | Память чата и Vane-инструменты чужого сервиса, другой system-промпт, риск выдумок; понадобился бы свой ретрай поверх чужого адаптера |
| Отдельный модуль/сервис на досье | Нет требования независимого деплоя/масштабирования; новый модуль = allowlist arch-тестов, ADR и второй деплой (ADR 2026-10-28-single-deployable-app-module) |
| Искать по всей базе профилей, а не по авторам чата | Раскрывало бы людей из других чатов; решение человека — только авторы этого `peer_id` |
| Пусть LLM определяет адресата по тексту | Недетерминированно и дороже: резолв, матчинг и уточнение — чистый домен с табличными тестами |
| Сохранять live-профиль, полученный при отсутствии сохранённого | Расширяет запись и PII без требования; сохранение профилей — зона `message-storage` при входящем сообщении (ADR 2026-11-10-vk-profile-human-details) |
| Искать группы по голому имени | Нет надёжного источника имени группы в сохранённых данных; только `club`/`public`-id или пересылка |
| Собственный outbox/дедупликация/rate limit | Нет требования; дубли at-least-once — известный размен, как у ответов и справки |
| Kill-switch ветки | Нет требования гасить без отката; always-on как у news, откат — предыдущий образ |
| Переносить публикацию в use case | Один вызывающий и один повод к изменению; условие апгрейда — второй потребитель текста досье |

## Известные пробелы (named gaps)

- **Имя — эвристика префикса/основы:** lowercase, `ё → е`, срезание хвоста гласных и `й/ь/ъ`, затем
  префикс. Уменьшительные вне префикса не находятся (`Паша` ≠ `Павел`), ложные совпадения решаются
  уточнением. Апгрейд — словарь/морфология уменьшительных при ложных срабатываниях.
- **Группы** — только `club`/`public`-id или пересылка; по имени группа не ищется.
- **Allowlist `details`:** телефоны, контакты, `counters`, `connections`, вложенные списки/карты
  (`career`, `universities`, `schools`, `relatives`) и неизвестные ключи не рендерятся; расширение
  таблицы — вместе с `VkUserProfileMapper`.
- **At-least-once без дедупликации:** повторная доставка события может дать повторный ответ; VK
  дедуплицирует только одинаковый текст через `random_id`, а текст LLM может отличаться.
- **Нет кэша ответов и rate limit:** LLM-вызов на каждый запрос; стоимость и абьюз ограничены только
  платформой.
- **Live-профиль не сохраняется:** у него нет истории и материализованной статистики, следующий запрос
  повторит вызов VK.
- **В групповом чате запрос достижим только после `requiredAnswer=true`** (упоминание бота или forward
  от бота) — следствие решения «только интент decision-модели», а не дефект резолва.
- **Наблюдаемость:** новых метрик и спанов нет; единственный новый лог — ERROR при отказе LLM (только
  `peerId` и простое имя класса); отдельного INFO-лога успеха нет.

## Последствия

- Четвёртый producer `ANSWER_MESSAGE` (после `ai-answer`, веток `answer-decision` и `chat-news-digest`);
  контракт события и `ResponseMessage` не менялся.
- Восьмое событие получило консюмера; промежуточное состояние «событие без потребителя» больше не
  существует. Публичный REST и схема БД не менялись.
- Появился новый PII-поток: профиль, история, статистика (включая активность из чужих чатов) и вопрос
  уходят в LLM-промпт и в INFO/OTLP-логи провайдера — принятый риск (ADR 2026-11-05-llm-provider-vllm-openai).
- Стоимость: один LLM-вызов (до трёх попыток порта) на каждый запрос «профиль»; лимитов нет — named gap.
- Откат — предыдущий образ: данные и схема не меняются, флагов нет; откат возвращает потерю запросов
  «профиль» (unknown routing key → ERROR с payload) — известно и приемлемо.
