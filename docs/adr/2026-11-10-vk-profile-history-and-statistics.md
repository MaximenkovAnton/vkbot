# 2026-11-10: Полный профиль VK, история изменений и статистика активности

- **Статус:** accepted
- **Дата:** 2026-11-10
- **Supersedes:** —
- **Amended by:** ADR 2026-11-10-user-statistics-materialization — материализованные агрегаты статистики
  автора вместо расчёта из `messages` (три таблицы, upsert в транзакции сообщения, backfill-скрипт);
  ADR 2026-11-10-vk-profile-human-details — человеческие поля профиля VK (`profile_details` вместо
  `profile_data`, `USER_FIELDS` 35, typed + человеческий diff); остальные пункты ниже остаются в силе.

## Контекст

Профиль хранился пятью полями (`first_name`, `last_name`, `screen_name`, `birth_date`, `city`), которые
запрашивались у VK через `users.get` с `fields = bdate,city,screen_name`. При актуализации профиль
перезаписывался поверх: прежние значения изменённых полей терялись, восстановить историю было нельзя.
Статистики по авторам не было: `messages` хранит `from_id`, `peer_id`, `date` и текст, но ни один
читающий API их не агрегировал.

Требование: собирать всё, что VK отдаёт о человеке (кроме аватарки/фото — использовать их негде и незачем),
хранить историю изменений профиля, считать активность автора: сколько пишет (число сообщений и средняя
длина), в каких чатах, в какие дни недели и часы.

## Решение

- **Полный ответ VK.** `users.get` запрашивается со всеми полями из документации, кроме `photo_*`,
  `crop_photo` и производных (`has_photo`): `about`, `activities`, `bdate`, `blacklisted`,
  `blacklisted_by_me`, `books`, `can_post`, `can_see_all_posts`, `can_see_audio`,
  `can_send_friend_request`, `can_write_private_message`, `career`, `city`, `common_count`, `connections`,
  `contacts`, `counters`, `country`, `domain`, `education`, `exports`, `followers_count`, `friend_status`,
  `games`, `has_mobile`, `home_town`, `interests`, `is_favorite`, `is_friend`, `is_hidden_from_feed`,
  `last_seen`, `lists`, `maiden_name`, `military`, `movies`, `music`, `nickname`, `occupation`, `online`,
  `personal`, `quotes`, `relation`, `relatives`, `schools`, `site`, `status`, `timezone`, `universities`,
  `verified`, `wall_comments`, `wall_default`. Список — константа `USER_FIELDS` в
  `VkGetUserProfilesBatchAdapter`.
- **Хранение ответа — JSONB-снимок.** `VkUserProfile.profileData: Map<String, Any?>` — весь ответ VK
  (топ-уровневые поля, вложенные объекты как `Map`/`List`), без фото-полей. Домен остаётся без фреймворков:
  ADR 2026-10-28-module-boundaries-and-layer-rules/L1 запрещает `com.fasterxml..` в `..domain..`,
  поэтому это обычная `Map`, а не `JsonNode`.
  В БД — `vk_user_profiles.profile_data JSONB`; сериализация только в output-адаптере
  `VkUserProfileTable`. Типизированные колонки остаются: `birth_date` — запрос именинников
  `daily-greetings`, `first_name`/`last_name`/`screen_name`/`city` — отображение имён и `GET /api/profiles/*`.
  Снимок и колонки пишутся одним upsert; при слиянии поле, которого VK не вернул (или вернул `null`),
  сохраняет прежнее значение — правило AC-message-storage-3 не меняется.
- **История — только изменения, JSONB.** Новая таблица
  `vk_user_profile_history(id UUID, profile_id BIGINT, changes JSONB, changed_at TIMESTAMPTZ)` с индексом
  `(profile_id, changed_at)`. Строка = одна актуализация, в которой что-то изменилось:
  `changes = {"field": {"old": <value>, "new": <value>}}` по изменившимся топ-уровневым полям снимка.
  `ProfileDataMerger` (`persistence/domain/profile`) считает слияние и diff без Jackson; сравнение
  канонизирует числа (`BigDecimal`) и не зависит от порядка ключей JSONB. Новые поля получают `old = null`,
  удалённых полей не бывает по правилу слияния. Первая запись профиля истории не пишет (её состояние —
  сама строка профиля); `last_updated` в diff не участвует. Для строк, сохранённых до этой версии
  (пустой `profile_data`), diff строится по типизированным полям, чтобы изменение не потерялось.
  `SaveUserProfilePort.SaveChanges` — `Map<String, Map<String, Any?>>?`; `null`/пустая карта — истории нет.
  Запись профиля и история — в одной транзакции `SaveUserProfileAdapter`.
- **Статистика — из журнала сообщений, без второй копии.** `messages` — источник истины; агрегаты
  считаются на чтении (`UserStatisticsReader`): число сообщений и `sum(length(message_text))`,
  средняя длина, `min/max(date)`, разбивка по `peer_id` (число, длина, средняя, последнее сообщение),
  гистограммы по часу и по ISO-дню недели (`extract(hour|isodow from date at time zone ...)`).
  Дни/часы — в зоне `statistics.timezone` (env `STATISTICS_TIMEZONE`, дефолт `Europe/Minsk`), потому что
  читателю нужна местная активность, а не UTC. REST: `GET /persistence/statistics/users/{id}` и
  `GET /persistence/profiles/users/{id}/history?limit=&offset=`. In-process портов и событий
  новых нет: потребителей статистики вне `persistence` пока нет.
- **Схема.** Один новый changeset `007-add-user-profile-data-and-history` (колонка `profile_data` +
  таблица истории). Старые changesets не правятся (конституция). Backfill статистики не нужен: она
  считается из уже сохранённых сообщений.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Типизированная модель на все поля VK | ~60 полей и вложенных структур; каждое изменение схемы VK — правка домена. Снимок JSONB переживает новые поля без миграции; для отображения хватает типизированных колонок |
| `JsonNode` в `VkUserProfile` | L1 запрещает `com.fasterxml..` в `..domain..`; `Map<String, Any?>` — тот же снимок, но framework-free |
| Отдельная таблица «поле → значение → дата» | Нормализация даёт строку на каждое поле на каждую актуализацию — ровно те `null`/дубликаты, которых просили избежать; JSONB-diff компактнее и читается одним запросом |
| Полный снимок в каждой строке истории | Дублирует неизменённые поля; diff отвечает на вопрос «что и когда изменилось» дешевле |
| Инкрементальные таблицы агрегатов (счётчики/чаты/часы) | Двойная запись и backfill-миграция; агрегаты могут разойтись с `messages`, а при текущем объёме чтение по индексу `from_id` дёшево. Условие апгрейда — медленный p95 статистики |
| Событие `STATISTICS_UPDATED` на каждый `MESSAGE_NEW` | Лишний хоп брокера и второй писатель в ту же БД; агрегация в том же процессе дешевле |
| Хранить часы/дни в UTC и пересчитывать на чтении | Гистограмму нельзя корректно пересчитать из UTC-бакетов при смене зоны; зона фиксируется на чтении и читается из конфига |
| Суммарные поля в `vk_user_profiles` (count, avg length) | Смешивает профиль VK и поведенческую статистику, которую можно пересчитать; отдельный read-эндпоинт чище |

## Известные пробелы (named gaps)

- `counters` и `military` VK отдаёт только при запросе ровно одного `user_id`; при батчевом запросе
  этих полей в ответе нет. Отдельные вызовы на каждого пользователя не делаются (риск rate limit).
- Набор полей — константа кода: появившееся у VK поле попадёт в снимок только после правки
  `USER_FIELDS`, но уже сохранённый снимок от этого не портится.
- У профилей, сохранённых до этой версии, `profile_data` пуст до первой актуализации; история за это окно
  пишется только по типизированным полям.
- История не ретенционируется и не чистится; фильтра по датам и пагинации сверх `limit/offset` нет.
- Статистика читает `messages` без периода: запрос по одному автору сканирует его сообщения; фильтр
  периода и материализованные агрегаты — условие апгрейда, не требование.
- У `length(message_text)` — символы Postgres, не байты и не «слова»; emoji считаются символами.
- Смена `STATISTICS_TIMEZONE` меняет бакеты только на чтении (ничего не пересчитывается и не хранится).
- Фото/аватарки не запрашиваются и не сохраняются намеренно; если появятся потребители — это отдельное
  решение.
- Профили групп (`vk_group_profiles`) остаются типизированными (`name`, `screen_name`): требование было
  про человека, а у групп другого набора полей нет; история групп не ведётся.

## Последствия

- Один запрос к VK возвращает полный профиль; ответ сохраняется целиком и переживает расширение VK.
- Обновление профиля больше не теряет прежние значения: они лежат в `vk_user_profile_history` и доступны
  по REST.
- Появились два читающих REST-эндпоинта в `persistence`; in-process контракты и события не менялись.
- Схема БД выросла на колонку `profile_data` и таблицу истории; старые данные не переписываются.
- Стоимость: `users.get` возвращает больше полей (тот же один вызов), статистика агрегирует `messages`
  на каждый запрос (named gap).
