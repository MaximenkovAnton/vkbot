# 2026-11-10: Материализованная статистика автора вместо расчёта из `messages`

- **Статус:** accepted
- **Дата:** 2026-11-10
- **Supersedes:** —
- **Amends:** ADR 2026-11-10-vk-profile-history-and-statistics — пункты про статистику: источник истины,
  вычисление на чтении, хранение бакетов, необходимость backfill и условие апгрейда «материализованные
  агрегаты». Профильные пункты и формат истории остаются в силе. Тело старого ADR не переписывается; в его
  шапку добавлена строка `**Amended by:**`.
- **Amended by:** —

## Контекст

[ADR 2026-11-10-vk-profile-history-and-statistics](2026-11-10-vk-profile-history-and-statistics.md) считал
статистику на чтении: `JooqUserStatisticsRepository` агрегировал `messages` по `from_id` при каждом
запросе `GET /persistence/statistics/users/{id}` — `count`, `sum(length(message_text))`, `min/max(date)`,
разбивку по `peer_id` и гистограммы `extract(hour|isodow ...)`.

Это ограничивает продукт:

- стоимость чтения растёт с числом сообщений автора: каждый запрос — скан и агрегация без фильтра периода;
- `messages` — журнал, а не витрина: ретенцию или архивацию сообщений нельзя ввести, не потеряв статистику;
- гистограммы по часу и дню недели считаются при каждом чтении, хотя зависят только от зоны, а не от
  запроса.

Требование: агрегаты материализуются при сохранении сообщения и обновляются в той же транзакции; чтение
идёт только из агрегатов и конвертирует UTC-бакет в зону на чтении; накопленные сообщения переигрываются
в агрегаты ручным SQL-скриптом. Формат `GET /persistence/statistics/users/{id}`, домен `UserStatistics`,
порт `FindUserStatisticsPort` и REST-контракт не меняются.

## Решение

- **Три агрегатные таблицы.** `user_statistics` — итоги на автора (PK `user_id`): `message_count`,
  `total_length`, `first_message_at`, `last_message_at`, `updated_at`; `user_chat_statistics` —
  автор×чат (PK `(user_id, peer_id)`): `message_count`, `total_length`, `last_message_at`;
  `user_hour_statistics` — автор×UTC-дата×UTC-час (PK `(user_id, utc_date, utc_hour)`): `message_count`,
  CHECK `chk_user_hour_statistics_utc_hour` (`utc_hour BETWEEN 0 AND 23`). Схема аддитивна, ретенции нет.
- **Запись — в транзакции сообщения.** `SaveMessageUsecase` после вставки в `messages` вызывает порт
  `UpdateUserStatisticsPort` (`UpdateUserStatisticsAdapter`, `@Transactional`) →
  `JooqUserStatisticsWriterRepository`; фиксированный порядок upsert'ов `user_statistics` →
  `user_chat_statistics` → `user_hour_statistics` (+1 к `message_count`, +длина в code points к
  `total_length`, `first_message_at = LEAST`, `last_message_at = GREATEST`, UTC-бакет
  `(utc_date, utc_hour)` из `date.withOffsetSameInstant(UTC)`). Сбой любого upsert'а откатывает всю
  транзакцию: сообщение и все три инкремента неразделимы. Длина считается в code points
  (`String.codePointCount`), чтобы совпасть с `length(text)` Postgres.
- **Чтение — только из агрегатов.** `JooqUserStatisticsRepository.findByUser` читает итоги, чаты и
  бакеты из трёх таблиц; гистограммы конвертируются в `statistics.timezone` на чтении
  (`(utc_date + utc_hour * interval '1 hour') AT TIME ZONE 'UTC' AT TIME ZONE {zone}`). Смена
  `STATISTICS_TIMEZONE` не требует пересборки агрегатов. При отсутствии строк — нули и пустые списки.
- **Backfill — ручной ops-шаг, не миграция и не рантайм-бин.**
  `src/persistence/src/main/resources/db/backfill/backfill-user-statistics.sql` не владеет транзакцией
  (в файле нет `BEGIN`/`COMMIT`): вызывающий запускает его под
  `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f backfill-user-statistics.sql`, поэтому
  ошибка любой строки откатывает всё. Скрипт требует остановленного писателя, берёт
  `SET LOCAL lock_timeout = '2s'` и `LOCK TABLE user_statistics, user_chat_statistics,
  user_hour_statistics IN ACCESS EXCLUSIVE MODE`, пересобирает агрегаты (`DELETE` + три
  `INSERT ... SELECT` из `messages` с `count(*)`, `sum(length(message_text))`, `min/max(date)` и
  UTC-бакетами) и выполняет `ANALYZE` трёх таблиц. Запуск идемпотентен (delete + rebuild в одной
  транзакции).
- **009 — только DDL.** `009-create-user-statistics-tables` — 3 `createTable` + 1 `sql`
  (`ALTER TABLE ... ADD CONSTRAINT ... CHECK`); включается после 008; 001–008 не редактируются.

## Что отменяется в ADR 2026-11-10-vk-profile-history-and-statistics

- «Статистика — из журнала сообщений, без второй копии» и «Backfill статистики не нужен»: агрегаты теперь
  хранятся, backfill обязателен для накопленных `messages`.
- «Хранить часы/дни в UTC и пересчитывать на чтении» как отклонённая альтернатива: UTC-бакеты — принятое
  решение, конвертация выполняется на чтении.
- «Материализованные агрегаты — условие апгрейда, не требование»: материализация — текущее требование.
- «Смена `STATISTICS_TIMEZONE` ничего не хранит» остаётся верным по эффекту (пересборки нет), но теперь
  она меняет конвертацию UTC-бакетов, а не вычисление из `messages`.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Считать на лету из `messages` (как раньше) | Дорогое чтение без периода и блокирует архивацию журнала; требование — материализация |
| Рантайм-бин `StartupEvent` для backfill | Скрытый долгий шаг на старте, гонка с писателем и непредсказуемый деплой; нужен явный ops-шаг с контролем |
| Одна широкая таблица агрегатов | Смешивает три ключа (автор, автор×чат, автор×час) и заставляет nullable-колонки; три узкие таблицы повторяют read-модель |
| Материализовать локальные часы/дни | Зона — параметр чтения; локальный бакет пришлось бы пересобирать при смене `STATISTICS_TIMEZONE`, а `AT TIME ZONE` на чтении точен на границе суток и DST |
| Заполнять агрегаты только новыми сообщениями без скрипта | Накопленные `messages` не попадут в статистику; нужен пересчёт истории |
| Индексы сверх PK на этом проходе | Префикс PK покрывает чтения по `user_id`; `(user_id, message_count DESC)` — условие апгрейда по p95 |

## Известные пробелы (named gaps)

- **Окно дрейфа.** После отката на образ без writer'а сообщения окна пишутся в `messages`, но не в
  агрегаты; согласованность восстанавливает ручной пересчёт тем же скриптом. Автоматического заполнения
  нет.
- **Backfill — ops-шаг:** требует остановки приложения (единственный писатель); при живой аппликации
  транзакции сохранения сообщений встают на upsert'ах до конца пересборки.
- **Дубликаты:** у `messages` нет уникального ключа, повторная доставка `MESSAGE_NEW` создаёт дубль
  сообщения и дубль в агрегатах; дедупликации нет.
- **Ретенции нет:** `user_hour_statistics` растёт ≤ 24 строк на автора в сутки, `user_chat_statistics` —
  ≤ числа чатов автора; удаление строк `messages` агрегаты не пересчитывает.
- **`updated_at`** пишется при каждом upsert и не читается приложением — ops-поле для поиска дрейфа.
- **`user_hour_statistics`** агрегируется за всё время автора; условие апгрейда — ретенция,
  партиционирование или материализация локального часа, когда p95 начнёт расти от числа строк.

## Последствия

- На каждое сохранённое сообщение — три upsert'а в той же транзакции: запись сообщения теперь зависит от
  трёх агрегатных таблиц, сбой статистики откатывает сообщение и уходит в retry-лестницу брокера.
- Чтение статистики дешевеет и перестаёт зависеть от объёма `messages`; гистограммы конвертируются в зону
  на чтении без пересборки.
- До запуска backfill у существующих авторов статистика отдаёт нули, пока сообщения не начнут попадать в
  агрегаты инкрементом или пока не выполнен скрипт.
- Backfill требует остановки приложения (писатель); окно дрейфа после отката — named gap.
- Новых модулей, зависимостей, событий, REST-эндпоинтов и ключей конфига нет; `statistics.timezone`
  сохраняет имя и дефолт, меняется только смысл (конвертация на чтении).
