# ADR 0007: LLM-провайдер — vLLM через OpenAI-совместимый API

- **Статус:** accepted
- **Дата:** 2026-11-05
- **Supersedes:** —

## Контекст

AI в рантайме отдаёт vLLM с OpenAI-совместимым API, а сборка была закреплена за Ollama: `:src:ai` и
`:src:app` подключали `quarkus-langchain4j-ollama`, DevServices поднимали контейнер Ollama, тестовая
HTTP-граница отвечала на `/api/chat`, документация и карта возможностей описывали этот endpoint.
Адреса, имени модели и ключа в репозитории нет — их задаёт деплой; модель одна на ответ, саммаризацию
и OCR.

## Решение

- Провайдер — `quarkus-langchain4j-openai` (та же версия из `gradle.properties:8`) в обоих модулях,
  объявляющих расширение: `src/ai/build.gradle.kts:41` и `src/app/build.gradle.kts:39`. Второго
  провайдера и ветвлений по провайдеру в коде нет: домен и use case провайдера не знают (ADR 0003).
- Код знает только «OpenAI-совместимый API», поэтому vLLM подключён как есть: `base-url` — корень
  OpenAI API вместе с `/v1`, расширение дописывает `/chat/completions`.
- Контракт деплоя — env-ключи без вендорной привязки (`src/app/src/main/resources/application.yml:59-70`):
  `AI_BASE_URL` и `AI_CHAT_MODEL` обязательны (дефолт-URL не добавляется — ADR 0006: отказ на старте
  лучше запроса в неизвестный хост), `AI_API_KEY` опционален с дефолтом `dummy`: vLLM без `--api-key`
  его игнорирует, а при включённой на сервере авторизации ключ передаётся тем же env.
- `quarkus.langchain4j.openai.max-retries: 2` сохраняет поведение повторов: LangChain4j считает
  `max-retries` как повторы после первой попытки, поэтому даёт три попытки провайдера на вызов. Вместе с
  трёхкратным повтором `SummarizationAiAdapter` отказ модели даёт 9 POST-ов на `/v1/chat/completions` —
  столько же, сколько до миграции.
- Одна chat-модель обслуживает ответ, саммаризацию и OCR: `Image` уходит тем же chat-вызовом как
  `image_url` со ссылкой на изображение (`ImageRecognitionOutputAdapter` строит `Image` из url, а не из
  base64), то есть картинку по ссылке загружает сам сервер модели. Отдельная именованная
  vision-конфигурация продублировала бы base-url и api-key, а `RecognizeImagesCommand` не вызывается ни из
  одного use case (карта возможностей).
- Тестовая HTTP-граница — WireMock: `quarkus.langchain4j.openai.base-url` = `baseUrl()/v1` и
  `api-key: test-key`, заглушка отвечает OpenAI-конвертом на `/v1/chat/completions`.
  DevServices LangChain4j выключены (`quarkus.langchain4j.devservices.enabled: false`):
  контейнер провайдера больше не нужен, LLM в тестах — WireMock.

## Последствия

- Смена адреса, модели или ключа LLM — правка env, а не кода. Второй провайдер потребует отдельного
  решения, а не флага в конфиге.
- Старт без `AI_BASE_URL`/`AI_CHAT_MODEL` падает с именем неразрешённого ключа, а не уходит молча на
  дефолтный публичный URL расширения.
- Главная ловушка миграции: у openai `base-url` — корень API с `/v1`, у ollama это был голый корень
  сервера. Зафиксировано в `docs/development/configuration.md` и `docs/development/deployment.md`.
- `max-tokens`/`max-completion-tokens` не задаются: лимит остаётся дефолтом модели, как было до
  миграции.
- OCR на модели без vision возвращает ошибку провайдера: отдельного фолбэка нет, как и раньше.
- Ссылки на изображения должны быть доступны серверу модели: адаптер передаёт url, а не байты, поэтому
  закрытый/локальный адрес картинки даст ошибку провайдера.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Собственный REST-клиент к LLM | LangChain4j уже даёт chat-модель, память, инструменты и разбор structured output; второй клиент дублировал бы это |
| `langchain4j-open-ai` без Quarkus-расширения | Расширение даёт CDI-провайдера, конфиг и интеграцию с трейсингом; без него — ручная сборка бинов |
| Второй провайдер и выбор по конфигу | В деплое один провайдер; ветвление по провайдеру усложнило бы код без требования |
| Дефолт-URL `api.openai.com` | Молчаливый запрос в публичный хост вместо явного отказа на старте |
| `max-tokens`/`max-completion-tokens` сейчас | Лимит не задавался и раньше; менять поведение в проходе миграции не нужно |
