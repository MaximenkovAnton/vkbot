# 2026-11-23: Inbox входящих и лидер-лиз опроса Bots Long Poll

- **Статус:** accepted
- **Дата:** 2026-11-23
- **Supersedes:** ADR 2026-11-05-bots-long-poll-transport — частично: пункты «Поддерживается ровно один
  экземпляр приложения» и «идемпотентности записи в `messages` по-прежнему нет». Транспорт (Bots Long
  Poll, `ts` в PostgreSQL, «дубликат вместо потери») остаётся в силе. ADR
  2026-11-10-user-statistics-materialization — частично: пункт «Дубликаты» в «Известных пробелах».

## Контекст

Приём событий VK держал ровно один экземпляр приложения: токен и сохранённая позиция `ts` одни на
сообщество, поэтому вторая реплика делила бы позицию с первой и теряла события (ADR
2026-11-05-bots-long-poll-transport). Из этого следовали два ограничения: горизонтальное масштабирование
приёма запрещено, а деплой — `Recreate` (остановить старый экземпляр, затем поднять новый), то есть с
простоем на каждой выкатке. Активный-активный опрос VK не рассматривается: семантика VK при параллельных
`a_check` не документирована.

Доставка при этом at-least-once: `ts` сохраняется только после успешной публикации `MESSAGE_NEW`, и
падение между публикацией и сохранением повторяет обновление. У `messages` не было уникального ключа, так
что повтор давал дубль сообщения, дубль статистики и повторные события; `random_id` ответа считался
SHA-256 от текста, peer и даты, а не из стабильного идентификатора входящего. Вопрос «нужен ли ответ»
тоже мог отработать дважды на одном обновлении.

Цель — снять требование «ровно один экземпляр» и убрать дубликаты, не теряя ни одного обновления.

## Решение

- **Inbox входящих.** Receiver регистрирует каждое обработанное обновление в `incoming_messages` (changeset
  `011-create-incoming-messages`): `id BIGSERIAL PRIMARY KEY`, `peer_id BIGINT`, `conversation_message_id
  BIGINT`, `payload JSONB` — сырой JSON события VK, `received_at TIMESTAMPTZ DEFAULT now()`; UNIQUE
  `(peer_id, conversation_message_id)` и индекс `received_at` под очистку. Регистрация идёт через
  share-порт `RegisterIncomingMessagePort` до публикации `MESSAGE_NEW`, upsert'ом
  `ON CONFLICT (peer_id, conversation_message_id) DO UPDATE SET payload, received_at RETURNING id`:
  повторная доставка того же обновления всегда возвращает тот же `id` и продлевает ретенцию. Сбой
  регистрации — сбой публикации: `ts` не сохраняется, обновление приходит снова.
- **Идентификатор записи — ключ дедупа в `messages`.** `Message` несёт nullable `inboxMessageId`
  (`InboxMessageId`), старые события в очереди без поля читаются. `messages.inbox_id BIGINT NULL` с
  UNIQUE-индексом `uq_messages_inbox_id`, без FK: inbox чистится через 24 ч, а сообщения хранятся дальше.
  `SaveMessageUsecase` вставляет сообщение первым (`INSERT … ON CONFLICT (inbox_id) DO NOTHING`), и при
  `inserted = false` не трогает профили и статистику и не публикует `MESSAGE_RECEIVED`/`SUMMARY_REQUESTED`;
  подавленный дубль логируется одной строкой INFO с `peerId`, `conversationMessageId` и `inboxId`, без
  текста сообщения. Событие без inbox id сохраняется как раньше: NULL в уникальном индексе не конфликтует.
- **Лидер-лиз.** Активный поллер один, и определяется он лизом в PostgreSQL (`long_poll_lease`, changeset
  `012-create-long-poll-lease`: `id SMALLINT PRIMARY KEY`, `owner VARCHAR(64)`, `lease_until
  TIMESTAMPTZ`). Owner — UUID инстанса; перед каждым `a_check` реплика вызывает `AcquireLongPollLeasePort`
  с `vk.inbox.lease-ttl` (40 с). Получив лиз — опрашивает VK; не получив — стоит в standby с паузой
  `vk.inbox.standby-pause` (2 с) и VK не трогает. После пересменки `ts` читается из `long_poll_position`,
  а не из памяти реплики; при недоступной БД опрос не идёт (VK копит очередь), `ts` не теряется. На
  `ShutdownEvent` лиз освобождается, поэтому штатный рестарт отдаёт лидерство сразу. Переходы
  логируются: INFO на получение, первый standby и release, WARN на takeover и потерю лиза; PII в строках
  нет.
- **`random_id` из inbox id.** `MessageSendUsecase` берёт
  `RandomId.ofInbox(id) = ((id - 1) mod 2_147_483_647) + 1` — положительный int32, `0` невозможен, повтор
  той же отправки даёт тот же `random_id`. Для synthetic-сообщений (саммари) и старых событий без inbox id
  остаётся прежний детерминированный SHA-256 от текста и peer; plain-отправки (поздравления) не меняются.
- **Автоочистка.** Записи старше `vk.inbox.retention` (24 ч) удаляются по cron
  `vk.inbox.cleanup-cron` (по умолчанию раз в час, `@Scheduled(identity = "inbox-cleanup")` в
  `:src:receiver`): каждая реплика независимо вызывает `PurgeIncomingMessagesPort` с `received_at < now -
  retention`, один `DELETE` за прогон, число удалённых строк уходит в INFO. `messages` очистка не трогает:
  FK между таблицами нет.
- **Конфигурация.** Четыре ключа `vk.inbox.*` объявлены в `application.yml` со значениями по умолчанию
  (`VK_INBOX_LEASE_TTL=40s`, `VK_INBOX_STANDBY_PAUSE=2s`, `VK_INBOX_RETENTION=24h`,
  `VK_INBOX_CLEANUP_CRON=0 0 * * * ?`), новых обязательных env нет; в `%test` cron `off`.

## Последствия

- **Реплики разрешены.** Экземпляров может быть несколько: активный поллер один (держатель лиза),
  остальные standby. После перехода допустим `RollingUpdate`; `Recreate` больше не требуется. Пересменка
  занимает не больше TTL, и опрос не останавливается на время выкатки.
- **Переходный деплой — один раз.** Прежний образ не знает ни inbox, ни лиза: вместе с новым он опрашивал
  бы VK с тем же `ts` и плодил дубли. Поэтому переход с версии до inbox — остановить старый образ, затем
  поднять новый; после перехода реплики и rolling update разрешены (порядок —
  [`docs/development/deployment.md`](../development/deployment.md)).
- **Граница гарантии дедупа — ретенция inbox (24 ч).** Повторная доставка старше ретенции получит новый
  inbox id и даст дубль; события без `inboxMessageId` (накопленные в очереди до релиза) сохраняются
  каждый раз. Накопленные до релиза дубли не чистятся, отдельного уникального ключа
  `(peer_id, conversation_message_id)` у `messages` нет.
- **Fencing не вводится.** TTL лиза (40 с) меньше read-timeout `a_check` (60 с), поэтому живой лидер
  изредка переживает свой лиз и коротко опрашивается параллельно; дубли этого окна гасит inbox, регресс
  `ts` принят решением.
- **PII в inbox — принятый риск Q1=B.** `incoming_messages.payload` хранит сырой JSON события VK, включая
  текст сообщения; текст и так лежит в `messages` и уходит в LLM, поэтому класс данных тот же (канон —
  §«PII и логи» в [`docs/development/configuration.md`](../development/configuration.md)). Строки удаляются
  на ближайшем прогоне cron-очистки после ретенции (24 ч + до часа при дефолтном расписании), read-API у
  inbox нет, свои логи receiver пишет только id и счётчиками.
- **Ежедневные поздравления при N репликах.** Расписание срабатывает на каждой реплике, но claim в
  `greeting_log` выигрывает одна: остальные получают конфликт и пропускают отправку, at-most-once на
  `(greeting_date, peer_id)` сохраняется.
- **Схема аддитивна.** Changesets 011/012 добавляют таблицы, nullable-колонку и индексы; предыдущий образ
  их не читает, поэтому откат на один релиз назад проходит без изменения схемы. После отката дедуп не
  работает (старый образ не заполняет `inbox_id`) и `incoming_messages` не чистится — таблица перестаёт
  расти и ждёт возврата нового образа или ручного `DELETE` по ретенции. Следующий номер changeset — 013.

## Отклонённые альтернативы

| Альтернатива | Почему нет |
|---|---|
| Активный-активный опрос VK | Семантика VK при параллельных `a_check` не документирована; лиз делает активным ровно один поллер без риска для `ts` |
| Лиз во внешнем брокере/Redis | PostgreSQL уже есть, а лиз — одна строка; вторая инфраструктура ради неё не нужна |
| Дедуп только в `messages` по `(peer_id, conversation_message_id)` | Не даёт стабильного id для `random_id`, требует changeset и зачистки накопленных дублей; inbox — тот же ключ плюс сырой payload и ретенция |
| Inbox хранит только ключ | Сырой JSON — то, ради чего inbox: разбор инцидента без второго хранилища; PII принят решением Q1=B |
| FK `messages.inbox_id → incoming_messages.id` | Inbox чистится через 24 ч, сообщения живут дольше; FK потребовал бы `ON DELETE SET NULL` и обнулял бы ключ дедупа |
| Fencing и защита `ts` от старого лидера | Окно перекрытия остаётся из-за read-timeout 60 с > TTL 40 с; дубли гасит inbox, отдельная защита — сложность без требования |
| Оставить `Recreate` и один экземпляр | Простой на каждой выкатке и запрет на горизонтальное масштабирование — ровно то требование, которое снимается |
